01 Le principe, en une minute

MediBet, ce sont deux applications séparées : le Patient parie sur son diagnostic, le Médecin le pose pour de vrai. Elles ne se parlent jamais directement — pas de state partagé, pas de canal privé, pas même un serveur commun qui nous appartiendrait. Tout ce qu'elles ont en commun est déposé sur le serveur FHIR du TP, sous forme de ressources FHIR, et relu par l'autre app depuis un autre poste.

C'est ce qui rend la démonstration honnête : l'app Patient tourne sur un ordinateur, l'app Médecin sur un autre, et le pari se résout quand même. Si le serveur FHIR est débranché, plus rien ne circule entre les deux.

Le schéma ci-dessous est la partie complète, du dossier créé jusqu'au rendez-vous de suivi. Les deux flèches accentuées sont le cœur du sujet : le diagnostic écrit par le Médecin, puis relu par le Patient.

02 Le contrat REST du serveur

Le serveur du TP expose une API REST FHIR classique, en minuscules et sans préfixe de version. Toutes les requêtes partent avec Content-Type: application/json, et le CORS est ouvert : le navigateur peut appeler le serveur directement depuis la page, sans proxy.

AppelCe que ça faitUtilisé pour
GET /api/{ressource}/{id}lire une ressourcePatient, Practitioner
GET /api/{ressource}lister toutes les ressources d'un typeBasic (état de jeu)
GET /api/{ressource}?filtrelister avec un filtre de rechercheObservation par patient
POST /api/{ressource}créer, le corps est la ressourcePatient, Observation, Appointment, Basic
PUT /api/{ressource}/{id}remplacer une ressource existanteBasic (dossier résolu, portefeuille)
DELETE /api/{ressource}/{id}supprimerprévu dans le client, jamais déclenché

Une particularité à connaître : les listes ne sont pas des Bundle

Un serveur FHIR canonique répond à une recherche par un Bundle de type searchset, dont les résultats vivent dans entry[].resource. Le serveur du TP, lui, renvoie un tableau JSON brut de ressources — vérifié en direct contre le serveur. Notre lecture d'Observation accepte donc les deux formes, ce qui rend l'app portable sur un vrai serveur FHIR sans rien changer :

var list = Array.isArray(response)
  ? response                                                  // serveur du TP
  : ((response && response.entry) || []).map(function(e){      // Bundle FHIR standard
      return e.resource || e;
    });

Vrais appels ou appels simulés

Une seule variable décide, calculée automatiquement au chargement :

var MOCK_MODE = !!(window.claude && window.claude.use);

Elle ne vaut true que dans le bac à sable d'un artifact Claude, où le réseau externe est bloqué : les réponses sont alors simulées côté client pour que la démo reste jouable. Partout ailleurs — site public, exécution locale — elle vaut false et chaque appel part réellement sur le réseau. La pastille du bandeau indique lequel des deux modes tourne, et la console FHIR (bouton en bas à droite des apps) affiche les 60 derniers appels avec leur méthode, leur chemin et la réponse du serveur : c'est la preuve visible, pendant la démonstration, que les échanges sont réels.

03 La chronologie d'une partie

Chaque étape ci-dessous correspond à un moment de jeu et aux ressources qu'il met en mouvement, dans l'ordre. Les fiches détaillent attribut par attribut ce qui part sur le réseau et pourquoi.

Étape 1 — Le patient existe comme ressource FHIR

Avant tout pari, le joueur doit être un Patient sur le serveur. Deux chemins : pour les identités connues de la démo, l'identifiant est câblé dans le code (PATIENT_IDS) et pointe vers une ressource créée en amont sur le serveur du TP ; pour un nom inconnu, l'app crée le Patient à la volée puis met son id en cache local.

Ce câblage n'est pas de la triche, c'est une correction de bug : l'id était auparavant mis en cache par appareil, donc un second poste sans ce cache recréait un patient différent — et le dossier ouvert d'un côté n'était plus le même de l'autre.

Étape 2 — Le dossier part sur le serveur

Le patient coche ses symptômes ; l'algorithme de pré-diagnostic croise ces symptômes avec la base de maladies et propose les cinq diagnostics les plus probables, chacun avec sa cote. Le tout est déposé comme une ressource Basic de type medibet-dossier — c'est cet objet que l'app Médecin verra apparaître dans sa file d'attente, depuis un autre ordinateur. Le détail de l'encodage est en section 4.

Étape 3 — La mise

Au moment de miser, l'app fait d'abord un GET /api/patient/{id} : c'est une vérification volontaire que le patient existe bien côté serveur avant d'engager des CoinPot, et elle est visible dans la console FHIR pendant la démo. Le pari lui-même (medibet-pari) et le portefeuille (medibet-patient) partent ensuite comme ressources Basic.

Étape 4 — Le médecin ouvre le dossier

L'app Médecin interroge GET /api/basic toutes les sept secondes : c'est ainsi qu'un dossier créé sur un autre poste arrive dans sa file. À l'ouverture d'un dossier, elle lit les deux identités impliquées.

Étape 5 — Le diagnostic officiel : l'Observation

C'est l'acte central du projet, et la seule vraie donnée clinique que MediBet produit. Le médecin choisit le diagnostic réel dans la base complète des maladies, et l'app publie une ressource Observation. Tout le reste du jeu — la résolution du pari, le gain, le rendez-vous — découle de cette écriture.

Étape 6 — Le patient relit le diagnostic et le pari se résout

Depuis son poste, le patient interroge lui-même le serveur. C'est la démonstration d'interopérabilité la plus parlante du projet : aucune information ne transite entre les deux apps, le Patient va chercher sur le serveur ce que le Médecin y a déposé.

Étape 7 — Le rendez-vous de suivi

Un pari gagné ouvre droit à une consultation de suivi, prise elle aussi sur la plateforme. C'est la troisième ressource écrite par le projet, et la seule qui engage l'avenir plutôt que de constater le passé.

04 Basic : le standard comme base de jeu

Un dossier de pari, une cote, un portefeuille de CoinPot : rien de tout cela n'est une donnée clinique, et aucune ressource FHIR dédiée n'existe pour ça. Le standard prévoit exactement ce cas avec Basic, une ressource générique dont le type réel est porté par son propre contenu.

Nous l'utilisons comme base de données partagée du jeu. L'intérêt est direct : aucun serveur ne nous appartient, et pourtant les deux apps partagent un état, sur deux ordinateurs différents, uniquement via la plateforme du TP.

L'encodage : un attribut par extension

Basic n'a pas de champs métier. On encode donc chaque champ dans une extension — le mécanisme d'extensibilité prévu par FHIR — et le type de l'objet dans code.text :

{
  "resourceType": "Basic",
  "code": { "text": "medibet-pari" },
  "extension": [
    { "url": "dossierId", "valueString": "6a9ec8…" },
    { "url": "pronostic", "valueString": "angine" },
    { "url": "cote",      "valueString": "3.4" },
    { "url": "mises",     "valueString": "[{\"name\":\"Romane Cano\",\"montant\":50,…}]" },
    { "url": "status",    "valueString": "ouvert" }
  ]
}

Les valeurs composées (listes, objets) sont sérialisées en JSON dans valueString, et reparsées à la lecture. Deux fonctions symétriques font tout le travail : gsEncode() à l'écriture, gsDecode() à la lecture, qui replace au passage l'id du serveur dans l'objet de jeu.

La synchronisation

Il n'y a ni websocket ni Subscription FHIR : chaque app relit GET /api/basic toutes les sept secondes, compare le résultat au précédent et ne redessine l'écran que s'il a changé — et jamais pendant qu'un champ de formulaire est en cours de saisie. C'est rustique, mais c'est ce qui tourne pendant la démonstration, et ça suffit largement à l'échelle d'une partie.

05 Conformité : ce qui l'est, ce qui ne l'est pas

Assumer les écarts vaut mieux que les laisser découvrir. Voici l'état exact du projet.

Ce qui est conforme

  • Les quatre ressources standard sont bien formées, avec leurs attributs obligatoires (resourceType, status, les références typées Patient/{id} et Practitioner/{id}).
  • Les références croisées sont réelles : l'Observation pointe vers un Patient et un Practitioner qui existent sur le serveur.
  • La recherche utilise un paramètre FHIR standard (subject.reference), pas une invention maison.
  • Basic est employé pour ce à quoi le standard le destine : ce qui n'a pas de type dédié.
  • La lecture accepte aussi bien le tableau brut du serveur du TP qu'un Bundle FHIR canonique.

Ce qui ne l'est pas — et pourquoi

À retenir pour la soutenance. L'interopérabilité technique est démontrée de bout en bout : deux applications, deux dépôts, deux déploiements, aucun état partagé, et un pari qui se résout quand même. L'interopérabilité sémantique — qu'un système tiers comprenne nos diagnostics — s'arrête au codage maison, et c'est le premier point de la liste des améliorations.
